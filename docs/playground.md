# The playground

The playground runs A0 itself in a browser, with nothing installed: a grammar on one side, a
program on the other, and the program's output. The grammar defines the language with `@hir`
forms (`docs/grammar.md`, "Languages without host code"), as for `a0 lang`, so editing the grammar
changes the language. It shows the program's syntax tree, its HIR and its core IR too, and errors
as the `a0` tool renders them, against the grammar or the program.

It is published from `main` at **https://dan-k391.github.io/a0/** (`.github/workflows/pages.yml`).
Its examples are Calc and Lispy (`examples/calc`, `examples/lispy`), two languages with the same
forms and different syntax.

## Building it

```
rustup target add wasm32-wasip1
WASI_SDK=/path/to/wasi-sdk sh playground/build.sh     # into target/playground
node playground/test.mjs target/playground
python3 -m http.server -d target/playground           # then open http://localhost:8000
```

The engine's C runtime is compiled with [wasi-sdk](https://github.com/WebAssembly/wasi-sdk)
(clang and a C library for WebAssembly; CI uses release 34, for Linux). The build works on Linux
and macOS; on Windows, build it in WSL.

## How it works

- **The engine** is `crates/a0-playground`, a small program built for wasm32-wasip1: the grammar
  layer, the HIR builder and lowering, the interpreter and the C runtime, without the native
  backend. It takes the grammar and the program as arguments (a page has no files) and a mode:
  `run`, `tree`, `hir` or `ir`. Built for the host, it is tested like any other crate.
- **The page** (`playground/`) is static: `index.html`, `app.js` for the editors, `worker.js`,
  which runs the engine in a Web Worker so that a program that never ends can be stopped, and
  `wasi.js`, the few WASI calls the engine makes (arguments, standard output and error, clocks,
  randomness) in some 110 lines. Each run instantiates the module afresh, so the runtime's state
  starts anew. A link (Copy link) holds the grammar and the program.
- **The runtime on 32 bits.** Generated code reads a few runtime fields as 64-bit words: an
  object's type in the collector's header, a type's family and interface table, an array's
  elements. On wasm32 a pointer is 4 bytes, so those fields are declared with `A0_WORD_PTR`: a
  pointer in the low half of a word whose high half stays zero (`a0rt.h`). The layout is the
  same on every target, and static checks in `gc.c` keep it so.
- **Calls into C.** The interpreter calls C functions with every argument as a 64-bit word,
  through a function pointer of a generic type. Natively the C compiler casts the pointer; in
  WebAssembly a call through a pointer of the wrong type traps, so the symbol table holds wrappers
  that take the words and convert them to the real parameter types, generated by
  `crates/a0-runtime/build.rs` from the prototypes in `a0rt.h`.

## Limits

- No native code: the playground interprets. Programs cannot read files, and standard input is
  empty; `std` functions that need them fail as they would on a system without them.
- Calls nest at most 1000 deep (10,000 natively): the interpreter recurses on the browser's own
  stack, about 1 MB. Deeper recursion stops with `panic: stack overflow`, exit 101.
- Output is shown up to a million characters.
- `clock()` is the time since the program started (WASI has no processor clock).
